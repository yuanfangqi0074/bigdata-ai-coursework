一句话理解

Skill 就是把"这件事该怎么干"写成一份可以反复使用的文件， 让 Agent 在需要时自己翻出来看。它解决的是一个很具体的痛点： 同样的要求，你不想每次都重新说一遍。

Anthropic 给的比喻是"给新人准备入职手册"。我在这个基础上补一句自己的体会： 提示词是当面口头交代，Skill 是写成文档存档。 口头交代说完就散了，下次还得再说；文档在那儿，谁需要谁来翻，而且可以改、可以版本管理、可以给别人。

学习目标

  • 能说清 Skill 与提示词的本质区别，不是"更长的提示词"
  • 能画出渐进式披露的三层结构，并解释每一层为什么那样设计
  • 能搭出一个可用的 Skill 目录，写出合规的 YAML 元数据
  • 能区分 Skill、MCP、提示词各自解决什么问题
  • 知道 Skill 的安全边界在哪里

核心机制与组成

目录结构

最小形态是一个包含 SKILL.md 的目录。SKILL.md 必须以 YAML 前置元数据开头，其中 name 和 description 是必填项：

---
name: concept-learning-material
description: 给定一个概念名称，生成一份结构完整的个人概念学习资料（HTML）……
---

# 概念学习资料生成器
（正文：流程、要求、自检清单）

复杂一点可以捆绑附加文件：

concept-learning-material/
├── SKILL.md          ← 必需，主指令
├── REFERENCE.md      ← 可选，详细参考
└── scripts/          ← 可选，可执行脚本

核心设计：渐进式披露（Progressive Disclosure）

这是 Skill 最关键的设计，也是它和"把一大段提示词存起来"的根本区别。 信息分三层，按需进入上下文：

层级内容何时加载上下文开销
第 1 层元数据：YAML 里的 name + description启动时就进系统提示每个 Skill 约 100 tokens
第 2 层指令：SKILL.md 正文判断相关时才读入建议控制在 5k tokens 以内
第 3 层资源与代码：附加文件、脚本需要时才读／才执行几乎不受限
第 3 层为什么"几乎不受限"？ 因为 Skill 存在于文件系统中。Agent 需要时按名字读，不需要就永远不进上下文。 更妙的是脚本：Agent 执行脚本时只拿到运行结果，脚本代码本身不进上下文。 这意味着一个 Skill 可以捆绑几十个参考文件却几乎不占上下文—— 正好绕开了上下文有限这个约束（见 llm-context.html）。

与相近概念的区别

解决什么问题作用域是否常驻上下文
提示词这一次要干什么单次会话是，全程占用
Skill这类事该怎么干跨会话、跨项目否，按需加载
MCP怎么连上外部工具和数据接口层否，通过协议调用

Anthropic 把完整的 Agent 架构拆成四层，各自的职责很清楚：

  • Agent 循环——负责推理，决定下一步做什么
  • 运行时——负责执行（代码、文件系统）
  • MCP 服务器——负责连接外部工具与数据
  • Skills 库——负责提供领域知识与流程

一句话记：循环负责想，运行时负责干，MCP 负责连，Skill 负责教。

一个重要时间点

2025 年 12 月 18 日，Anthropic 把 Agent Skills 发布为开放标准， 推动它像 MCP 一样跨平台可移植——同一个 Skill 应该能在不同的 AI 平台上使用。 这解释了为什么 Skill 采用"文件夹 + Markdown"这种朴素格式： 没有私有协议，才谈得上可移植。

具体应用场景

场景：本仓库在用的 concept-learning-material

你正在读的这份资料，就是由这个 Skill 生成的。

没有 Skill 时：要生成三份资料，我得把"要包含个人解释、核心机制、应用场景、 易混淆点、可核查来源、自测题，而且来源必须实际验证过"这段话重复说三遍， 还不敢保证三遍的说法完全一致。

有了 Skill 之后：这些要求写一次，存在 SKILL.md 里。 生成三份资料时，Agent 自己读取并遵守。更重要的是它可复用—— 下次要学"向量数据库"，不用重新描述任何要求，直接说概念名就行。 而且它不绑定这三个概念：流程和自检标准对任意概念都成立。

这就是 Skill 的价值：把一次性的口头要求，变成可版本控制、可共享、可持续迭代的资产。

容易混淆的问题与使用边界

① Skill 不是"更长的提示词"。 区别不在长短，在这四点：存在于文件系统中、按需加载、 可以捆绑代码、可以组合使用。 如果只是把一大段提示词存成文件，但没有渐进式披露，那只是个文本文件。
② description 写不好，Skill 就等于不存在。 第 1 层元数据是 Agent 判断"该不该用这个 Skill"的唯一依据。 Anthropic 明确提醒：要特别留意 Skill 的命名和描述，Agent 靠它们做触发决策。 写得含糊，Skill 永远不会被调用——你可能还以为它坏了。
③ Skill 能带可执行代码，这是安全边界。 Skill 可以捆绑脚本供 Agent 执行，这也意味着恶意 Skill 可能引入漏洞或引导 Agent 做出非预期行为。 官方建议：只从可信来源安装；对低信任来源，安装前必须审计， 重点看代码依赖和捆绑资源，警惕任何指向不可信外部网络地址的指令。
④ Skill 解决"知识在哪"，不解决"上下文够不够"。 渐进式披露缓解了上下文压力，但不是万能的。 如果 Skill 正文写得臃肿，或者 Agent 一次触发了太多 Skill，照样会把上下文撑满。 它和上下文管理是两个层次的问题。
⑤ 不是所有重复任务都值得做成 Skill。 一次性的活直接说就行。Anthropic 观察到的 Skill 规模跨度很大： 简单的约 100 行（模板与格式），中等的约 800 行（数据获取 + 建模）， 复杂的 2500 行以上（编排多个分析工具）。 判断标准很简单：这件事你会在未来重复三次以上吗？

自测问题

  1. 为什么 SKILL.md 的 description 字段比正文更需要打磨？写砸了会发生什么？
  2. 一个 Skill 捆绑了 20 个参考文件，会不会撑爆上下文？请结合渐进式披露解释。
  3. Skill 和 MCP 各自解决什么问题？如果一个任务既要连外部数据库、又要按公司内部流程产出报告， 两者分别承担什么角色？
  4. 有人说"Skill 就是把常用提示词存成文档"。这个说法错在哪？至少说出三点区别。
  5. 从网上下载了一个陌生 Skill，里面带 Python 脚本。你应该做什么？为什么？
