概念学习资料：Agent

生成工具：concept-learning-material Skill ｜ 生成日期：2026-09-04 ｜ 课程：大数据与人工智能

一句话理解

Agent 不是"更聪明的模型"，而是把下一步做什么的决定权交给了模型的系统。 判断一个系统是不是 Agent，不看它用了多强的模型，只看一件事：决策权在代码里，还是在模型里。

这个判断标准是我读 Anthropic 的工程博客后自己提炼的。原文给了 Workflow 和 Agent 的定义， 但真正让我记住的是它背后那句潜台词——架构选错的代价，是多花几倍的钱和延迟，换来一个更难调试的系统。 所以与其记定义，不如记这条判据。

学习目标

  • 能说清 Agent 与 Workflow 的分界，拿到一个系统能判断它属于哪一类
  • 能画出 Agent 的运行循环，并指出每一轮里什么进了上下文
  • 能举出一个 Agent 真正比固定流程更合适的场景，也能举出一个不该上 Agent 的场景
  • 知道 Agent 的主要失效模式，以及为什么"自主性"是有代价的

核心机制与组成

运行循环

Agent 的核心是一个不断重复的循环：

规划（plan）→ 行动（act）→ 观察（observe）→ 回到规划
  1. 接到一个目标，模型决定这一步该做什么
  2. 调用一个工具（查数据库、跑代码、搜索、读文件）
  3. 工具返回的结果作为新信息进入上下文
  4. 模型基于更新后的上下文，重新决定下一步
  5. 重复，直到达成目标或触发停止条件

关键在第 3、4 步：工具返回的结果会真实改变下一步的决策。 这正是它和"按剧本走完所有步骤"的根本区别。

组成要件

组成部分作用缺失会怎样
目标循环的终点判据模型不知道何时该停
工具集模型能采取的行动退化成纯对话，无法影响外部世界
上下文每一轮的决策依据看不到历史，无法连续推理
停止条件最大轮数、超时、预算上限可能无限循环，成本失控

基础构建块：增强型 LLM

Anthropic 把 Agent 系统的最小单元称为增强型 LLM： 一个被配上检索、工具、记忆的大模型，并且模型能自己决定什么时候查、用哪个工具、记住什么。 所有复杂的 Agentic 系统，都是在这个块上叠加出来的。

Workflow 与 Agent 的分界

WorkflowAgent
路径由代码预先定义由模型动态决定
可预测性高低
成本与延迟相对可控随轮数线性上升
适合任务边界清楚，要求稳定一致步骤数量事先说不清
Anthropic 给出的默认值很反直觉：先找最简单的方案，很多场景根本不需要 Agent。 把单次调用加上检索和示例优化好，往往就够了。2026 年 3 月 Claude 官方博客进一步把生产中最常见的 模式收敛为三种：串行、并行、评估者-优化器，并建议默认从串行起步。

具体应用场景

场景：客服处理"吊牌扔了想退货"

用户说："我上周买的鞋想退，但吊牌已经扔了。"

系统需要：查订单确认购买时间和金额 → 检索退货政策，判断无吊牌是否影响 → 查该用户的历史退货记录 → 决定是批准、拒绝还是转人工 → 若批准则调用退款接口 → 组织回复。

为什么这里适合 Agent：步骤的数量和走向取决于查出来的结果。 如果用户是老客且无异常退货记录，可能两步就结束；如果订单超过 30 天，会走到完全不同的分支。 这种"路径无法事先写死"的特性，正是 Agent 的用武之地。

容易混淆的问题与使用边界

① 不是所有"AI 应用"都是 Agent。 把用户问题分类后转给不同提示词，这是 Workflow（路由模式），不是 Agent。 判断标准始终是"决策权在谁手里"，而不是系统自称什么。
② 自主性是有代价的。 Agent 用更高的延迟和成本去换任务表现。而且错误会累积—— 单步的小错会在后续轮次被当作事实继续推理，滚雪球式放大。 自主性越高，这个风险越大。
③ 上下文是硬约束。 Agent 每跑一轮，工具返回结果就写入上下文。跑几十轮后， 早期的约束可能被挤到中间甚至挤出窗口，导致 Agent 开始违反最初的要求。 这不是模型"变笨了"，见配套资料 llm-context.html。
④ Agent 解决不了反馈缺失的问题。 Anthropic 指出客服和编程之所以适合 Agent，是因为它们都有强反馈闭环 （客服有解决率，编程有测试运行结果）。 如果一个任务连"做对了没有"都无法判断，加 Agent 只会让失败更难被发现。
⑤ 框架会遮蔽问题。 各类 Agent 框架降低了上手门槛，但抽象层会挡住真实的提示词和响应， 出问题时很难调试。官方建议先用 API 直接跑通，要用框架就必须搞懂它底下在做什么。

自测问题

  1. 一个系统把用户问题分成三类，每类走不同的提示词和工具集。它是 Workflow 还是 Agent？说明你的判断依据。
  2. 为什么 Anthropic 建议"优先找最简单的方案，只在必要时增加复杂度"？如果违背这条，具体会在哪些指标上付出代价？
  3. Agent 的停止条件为什么必须显式设置？如果只靠模型自己判断"做完了"，可能出现什么问题？
  4. 举一个你身边"看起来该用 Agent，其实用固定流程更好"的例子，并说明理由。
