一句话理解

上下文不是模型的记忆，而是一次性的工作台面。 模型每次生成时能"看到"的全部内容就是上下文；生成结束，台面清空，什么都不留下。 更要紧的是：这是一张面积有限的台面，系统提示、检索资料、对话历史、工具结果、输出空间 全在上面抢位置。塞得多，不等于用得好。

"工作台面"这个比喻是我自己的说法，用来对抗我最容易犯的错——把上下文当成硬盘。 Anthropic 原文的说法更精确：上下文是边际收益递减的有限资源 （"a finite resource with diminishing marginal returns"）。 我加"一次性"这层意思，是因为很多人（包括最初的我）会以为多轮对话里模型"记住了"什么， 其实它只是每次都把历史重新读一遍而已。

学习目标

  • 能列出上下文里到底装着哪几样东西，并说出它们在争抢什么
  • 能解释为什么"窗口变长"不等于"能力变强"，并给出可验证的证据
  • 能区分上下文溢出（报错）与上下文腐烂（静默变笨），知道后者更危险
  • 掌握至少三种应对长上下文的工程手段，并知道各自的适用与风险

核心机制与组成

上下文里装着什么

组成部分说明谁来占
系统提示角色、规则、约束开发者
检索内容RAG 召回的文档片段检索系统
对话历史之前所有轮次的问答累积产生
工具结果每次工具调用返回的原始数据这个最容易失控
输出空间留给模型生成回答的余量模型

它们共享同一个 token 预算。工具结果多占一点，对话历史就少一点。 Anthropic 把它叫做注意力预算（attention budget）：每引入一个新 token，都会消耗一部分预算。

为什么长度会伤害质量

Anthropic 给出的原因链是：

  1. 架构层面：Transformer 让每个 token 都要和所有其他 token 建立联系， n 个 token 产生 n² 量级的成对关系。上下文越长，模型捕捉这些关系的能力被摊得越薄。
  2. 训练分布：训练数据里短序列远多于长序列，模型对超长距离依赖的经验本来就少。
  3. 结果是梯度而非断崖：原文强调这是 "a performance gradient rather than a hard cliff"—— 模型在长上下文下依然很强，只是检索精度和长程推理的精度下降。
"as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases."
—— Anthropic, Effective context engineering for AI agents

Chroma 的 Context Rot 研究：几个反直觉的实测结论

Chroma 在 2025 年 7 月的报告里测了 18 个模型 （5 个 Anthropic、7 个 OpenAI、3 个 Google、3 个 Qwen），保持任务复杂度不变、只改变输入长度。 结论比我预想的更细，其中两条跟网上常见的说法对不上：

反直觉发现一：结构连贯反而更差。 在全部 18/18 个模型上，把 haystack 的句子打乱之后，模型表现 优于保留原始逻辑连贯性的版本。去掉局部连贯性会持续提升性能。 这说明"把材料组织得更有逻辑"未必对模型更友好，得靠实测而不是想当然。
反直觉发现二：他们没观测到典型的"中间迷失"位置效应。 在他们的 NIAH 实验（8 种输入长度 × 11 个 needle 位置）中， 没有发现显著的位置差异。这一点必须说清楚—— "中间迷失"来自 Liu 等人 2023 年的另一项研究，而 Chroma 的实验没有复现出位置效应。 两者测的不是同一件事，不能混为一谈。

报告中稳定成立的是另外几条：

  • 长度本身就会降低可靠性：任务复杂度不变、只加长输入，性能依然下降。
  • 干扰项即使只有一个也会拖后腿：加 1 个干扰项就低于基线，加 4 个进一步恶化。
  • 聚焦输入远胜全量输入：LongMemEval 实验里，只给相关的约 300 tokens 显著优于给完整的约 113k tokens。因为全量输入迫使模型同时做"检索 + 推理"，而聚焦输入只需推理。
  • 不同模型家族失败方式不同：Claude 系列倾向保守弃权（宁可说找不到）， GPT 系列更容易给出自信但错误的答案。

报告自己没有给出确定机制，明确说这需要更深入的机械可解释性研究。 这点我觉得很值得学习——一份诚实的报告会写清楚自己不知道什么。

具体应用场景

场景：代码 Agent 做大型仓库迁移

一个 Agent 被要求把一个项目从旧框架迁到新框架。它会反复读文件、跑测试、看报错堆栈、 改代码、再跑测试。Anthropic 指出，这类任务"跨越几十分钟到数小时的连续工作"， token 数必然超出上下文窗口。

会出什么问题：几十轮之后，项目开头定下的迁移规范被挤到上下文深处， 或者干脆被挤出去。Agent 看起来一切正常、没有报任何错，但开始写出不符合新框架约定的代码。 这就是典型的上下文腐烂——静默劣化，监控系统抓不到。

工程应对（Anthropic 给出的三种手段）：
  • 压缩（Compaction）：第一手段。对话接近上限时让模型总结， 保留架构决策、未解决的 bug、实现细节，丢弃冗余的工具结果。Claude Code 的做法是 用压缩后的上下文 + 最近访问过的 5 个文件继续。调优顺序是先保召回率、再提精确率。
  • 结构化笔记：让 Agent 把进度写到上下文之外的文件（如 NOTES.md）， 上下文重置后再读回来。
  • 子 Agent 隔离：主 Agent 只做协调，探索工作交给子 Agent。 子 Agent 可以消耗数万 token 深挖，但只回传 1,000–2,000 tokens 的蒸馏摘要。

容易混淆的问题与使用边界

① 上下文窗口 ≠ 有效容量。 厂商宣传的窗口是"能塞多少"，不是"能用好多少"。Chroma 的数据说明， 即便是最新的前沿模型，在简单任务上也会随输入变长而退化。
② 溢出和腐烂是两回事，后者更危险。 上下文溢出是硬性报错，超过窗口上限，API 直接报错，容易发现。 上下文腐烂是静默的：没报错，但输出质量一路下滑。 生产环境里真正难查的是后者。
③ 上下文不是记忆，没有跨会话持久性。 你以为模型"记得"上周的对话，其实只是那段记录被重新塞进了上下文。 要真正的持久化，得靠上下文之外的存储（笔记文件、memory tool、数据库）。
④ "多塞点资料更保险"常常适得其反。 LongMemEval 的数据很直白：300 tokens 的聚焦输入打不过 113k 的全量输入？不，是反过来—— 聚焦输入显著更好。无关内容不是中性的，它会主动损害性能。
⑤ 压缩本身也有风险。 Anthropic 明确警告：过度激进的压缩会丢掉"当时看起来不重要、后来才显出价值"的细节。 所以顺序是先保召回、再删冗余，不能一上来就猛删。
⑥ 确定性任务不该指望 LLM。 Chroma 的重复词复制实验显示，连"复制一串词"这种程序本该零误差的任务， 模型在长输入下都会出错、拒绝或凭空生成随机词。 这类活应该交给传统代码，而不是往上下文里塞。

自测问题

  1. 一个 Agent 跑了 50 轮，一次错都没报，但开始违反项目开头定下的规范。最可能是什么原因？你会怎么验证这个猜测？
  2. Chroma 的实验里，"聚焦输入（约 300 tokens）"比"全量输入（约 113k tokens）"表现更好。 这个结果说明了什么？它和"上下文窗口越大越好"的说法冲突在哪里？
  3. 有人说"把资料组织得更有逻辑，模型就更好懂"。Chroma 的发现对此提出了什么挑战？
  4. 上下文溢出和上下文腐烂，哪个在生产环境更危险？为什么？
  5. 如果要你给一个长任务 Agent 设计上下文策略，压缩、结构化笔记、子 Agent 隔离 你会按什么顺序考虑？各自的适用条件是什么？
